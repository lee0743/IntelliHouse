## 소견 (직관과 반대)

### 1. Sonnet이 Haiku보다 낫지 않았다
이 태스크에서 **더 큰 모델이 더 나은 결과를 주지 않았다** (Haiku 87% > Sonnet 78%). 표본 N=5라
차이 상당 부분은 노이즈지만, 방향성은 분명하다: 모델 업그레이드는 해결책이 아니다.

### 2. 실패가 몰린 두 곳 모두 모델 업그레이드로 안 풀린다
- **전략 아님(잡담)**: Sonnet이 오히려 더 나쁨(형식실패 4/5). 더 유능·친절한 모델일수록 잡담에
  JSON `not_a_strategy` 대신 **자연어로 도우려 해서** 출력 계약을 더 자주 깬다. → **structured output이 해결**
  (§0.4, schemas/). 모델을 키우면 악화되기까지 한다.
- **모호한 다중조건 반대신호**: 두 모델 다 취약(Haiku 1/5, Sonnet 0/5). 단일 스트레스 실행에서 통과했던 건
  운이었다. 이게 **진짜 남은 soft spot** — 형식실패(반대신호 지시 스키마 혼란) + 판단실패(clarification 대신
  target:"all" 맹목 방출)가 섞여 있다.

### 3. 결론: 아키텍처 명제 재확인
> 실패 표면 = **출력 형식**(structured output으로 제거) + **한 개의 어려운 판단 케이스**(프롬프트·few-shot로 개선).
> 어느 쪽도 "더 큰 모델"로는 안 풀린다.

MVP 해석기는 **Haiku + structured output**이 비용/성능상 합리적. 남은 작업은 다중조건 반대신호
케이스의 exit 프롬프트 강화(전용 few-shot + clarification 예시)이며, 이건 모델이 아니라 프롬프트 문제다.

## 개선: exit 프롬프트 강화 후 (Haiku, N=5)

남은 soft spot(모호한 다중조건 반대신호)에 대해 exit 프롬프트를 강화 —
"조건 2개 이상이면 target 임의 결정 금지, needs_clarification + 대상 선택 질문" 규칙 명시 +
다중조건 전용 few-shot(예시 2, EMA/CCI로 테스트 케이스와 무겹침) 추가.

**검증됨**: 마지막 판단 soft spot은 **프롬프트(few-shot) 한 번으로 완치**됐다. 모델 업그레이드가 아니라
프롬프트가 답이라는 A/B 결론과 정확히 일치. 남은 형식실패 2건(혼입/잡담)은 structured output 몫.
